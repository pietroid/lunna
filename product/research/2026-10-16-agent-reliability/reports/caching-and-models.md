# Cut round trips, compute doubts, re-test models

For Lunna's agent, the main finding is that **prompt caching, routing tweaks and model choice matter much less than the RFC's structural changes**. A ~2k-token fixed prefix sits **below Gemini 3.x's 4,096-token caching minimum**, so it will never cache by itself. OpenRouter's own metadata also flags Gemini 3.x endpoints as not supporting implicit caching, which contradicts its docs. Latency sorting and model fallbacks exist and work as the RFC describes, with two catches. Fallbacks are not documented to fire on timeouts, and latency sorting turns off the sticky routing that implicit caching relies on. The clarification research agrees on one point: **whether a model asks is its own disposition, and it is unreliable in both directions**. Under the same harness, Gemini 3 Flash asked in **0%** of sessions and GPT-5.2 in 52%. Prompting does not fix this. Value-of-information gating over tool parameters does. That supports the RFC's design, where the server computes doubts and the model only phrases them. On models, the landscape has moved since the RFC's framing. `gemini-3.1-flash-lite` is no longer the newest Flash-Lite (3.5 Flash-Lite is), the current Flash is 3.8, and **Claude Haiku 5.5 is now the cheapest of the candidates on list price** ($0.10/$0.50 per 1M, against $0.25/$1.50). No public tool-calling benchmark covers any of the three candidates, so the RFC's in-house pass^k eval is the only real basis for the choice, not a nice-to-have.

## A 2k-token prefix never reaches Gemini's 4,096-token cache floor

Google enables implicit caching by default for every Gemini 2.5-and-newer model ([Gemini API caching](https://ai.google.dev/gemini-api/docs/caching)), and OpenRouter says the same: implicit caching on Gemini is automatic and needs no `cache_control` ([OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). The binding constraint is size. Google's minimum cacheable prefix is **4,096 tokens for Gemini 3 models "with exceptions"**, and **6,144 tokens for implicit caching on 3.0 Flash Preview, 3.7 Flash and 3.8 Flash** ([Vertex context cache overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)). Neither Google page has a row for Flash-Lite, so 4,096 for `gemini-3.1-flash-lite` is the Gemini 3 default, not a stated figure. OpenRouter's caching page still lists 2.5-era minimums (1,024 for 2.5 Flash) and is stale on this point.

There is also a contradiction to resolve before relying on any of this. OpenRouter's live endpoint metadata for `google/gemini-3.1-flash-lite` lists cache-read and cache-write prices on all eight endpoints, but sets **`"supports_implicit_caching": false` on every one of them**, and the same holds for 3.8 Flash, 3.5 Flash-Lite and 3 Flash Preview ([OpenRouter endpoints API](https://openrouter.ai/api/v1/models/google/gemini-3.1-flash-lite/endpoints)). That flag most likely controls OpenRouter's sticky routing, which sends a session back to the provider that last served a cached request ([OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). So Google may still give implicit hits while OpenRouter's load balancer spreads requests across AI Studio and Vertex, which are presumably separate caches. This is an inference, and one experiment settles it: send the same prefix of more than 4k tokens twice within a minute and read `usage.prompt_tokens_details.cached_tokens` ([OpenRouter usage accounting](https://openrouter.ai/docs/guides/administration/usage-accounting)).

When hits do happen, they are cheap. OpenRouter's live price for a cache read on 3.1 Flash-Lite is **$0.025/M, 10% of the $0.25/M input price**. That matches Google's 90% discount ([Vertex](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)) and contradicts the "0.25x" still printed in OpenRouter's docs. Explicit caching through OpenRouter uses Anthropic-style `cache_control` breakpoints, and only the last breakpoint counts for Gemini. A write costs the input price plus five minutes of storage ($0.0833/M on Flash-Lite), and the cache has a **fixed 5-minute TTL that reads do not extend** ([OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). There is one trap specific to Gemini. Once cached, `systemInstruction` is immutable, so dynamic content such as `now` or the day snapshot has to go in a later `user` message, never at the end of the system message ([OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). No primary source says whether `tools`, `tool_choice` or `response_format` affect hits. The safe rule is to keep the tools array byte-identical across all calls and never drop a tool on the last step.

The arithmetic shows how little this matters here. At $0.25/M, a 2k-token prefix costs about **$0.0005 per call**. The RFC's preload (§5.5) puts 1–3k tokens of day context into every turn, but that context changes from turn to turn, so it sits after the cacheable prefix rather than inside it. Across turns, the cacheable part stays under the floor. Within a turn, calls 2–4 can hit once the accumulated prefix passes 4k. But the RFC's main latency fix brings the common case down to **one call**, and then there is no second call to benefit. Caching should be measured and kept if it comes for free. It is not worth engineering around, and padding the prompt to 4k just to qualify is a bad trade. Nobody publishes how much a Gemini cache hit cuts time to first token, so the latency benefit is unquantified too.

## Latency sort and fallbacks work, but neither covers a slow call

OpenRouter's routing works as the RFC assumes, with caveats that change the configuration. `provider.sort: "latency"` turns off default load balancing (which otherwise favours cheap providers, weighted by inverse-square price) and orders endpoints by latency. `preferred_max_latency` and `preferred_min_throughput` add **soft** p50–p99 preferences over a rolling 5-minute window that "should therefore never prevent your request from being executed" ([OpenRouter provider selection](https://openrouter.ai/docs/guides/routing/provider-selection)). `models: [...]` falls back on any error from the primary model, including context length, moderation, rate limits and downtime, and billing follows the model that actually served the request. But the fallback docs **never mention timeouts**, and if the fallback also fails, its error is returned ([OpenRouter model fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks)). A slow call that eventually succeeds triggers nothing. So the RFC's client-side ~20 s timeout with one retry is necessary in NestJS, not redundant.

Two settings interact in ways the RFC does not mention. First, **sorting and sticky caching compete**: both choose the provider, and sticky routing is skipped entirely when `provider.order` is set ([OpenRouter prompt caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). Since caching barely pays here, latency should win. Second, OpenRouter exposes service tiers. `service_tier: "priority"` (or the `:nitro` suffix, which sorts by throughput and admits priority endpoints) is available for 3.1 Flash-Lite on both AI Studio and Vertex. Priority is not guaranteed, and it falls back to default endpoints, with billing following whichever endpoint served the request ([OpenRouter service tiers](https://openrouter.ai/docs/guides/features/service-tiers)). Priority costs more (its cache read is $0.045/M against $0.025/M), but for an interactive agent at these volumes the difference is fractions of a cent. **Avoid flex.** It returns capacity errors instead of falling back upward, and on 2026-10-16 the Vertex global flex endpoint showed about **53% uptime over 30 minutes** ([OpenRouter endpoints API](https://openrouter.ai/api/v1/models/google/gemini-3.1-flash-lite/endpoints)).

The biggest latency lever is probably not routing at all. 3.1 Flash-Lite supports thinking levels from minimal to high ([OpenRouter performance page](https://openrouter.ai/google/gemini-3.1-flash-lite/performance)), and for a model that only has to classify intent, `reasoning_effort` at minimal or low should matter more than any provider choice. That is an inference. No source publishes time-to-first-token for this model: OpenRouter's endpoints API returned `latency_last_30m: null` everywhere. A secondary, unverified report says 3.7 and 3.8 Flash reject "minimal" thinking ([computingforgeeks](https://computingforgeeks.com/gemini-3-8-flash-released-features-benchmarks/)). If true, that puts a latency floor under upgrading to the current Flash. The concrete configuration this points to: `provider: { sort: "latency" }`, `models: ["google/gemini-3.1-flash-lite", "google/gemini-3.5-flash-lite"]`, optionally `service_tier: "priority"`, low reasoning effort, a stable `session_id`, a 20 s client timeout with one retry on a 5xx, timeout or empty reply, and per-call logging of `cached_tokens`, `cost`, the served `model` and elapsed milliseconds.

## Gemini under-asks, so the doubts must come from the server

The 2025–2026 work on clarification converges on one diagnosis: **a model's tendency to ask is a trait of the model, not something prompting reliably controls**. In the natural-ask study of *Ask Early, Ask Late, Ask Right*, 100 TheAgentCompany sessions per model with an `ask_user` tool available, GPT-5.2 asked in **52%** of sessions ("over-clarifier"), Claude Sonnet 4.5 in **23%** ("balanced"), and **Gemini 3 Flash in 0%**, labelled an "under-clarifier" that "never asks" ([arXiv 2605.07937](https://arxiv.org/html/2605.07937v1)). SpecBench sees the same pattern in products: Gemini CLI "stops querying the user early and jumps into execution mode", while Claude Code and Cursor CLI keep asking until "more interactions even reduce the quality of the resulting spec sheet" ([arXiv 2606.20585](https://arxiv.org/html/2606.20585)). Ambig-SWE finds that models "almost never interact, even for severely underspecified inputs" unless pushed, and that the pushing behaves inconsistently. Strong encouragement raised Sonnet 4's detection to 89% but cut DeepSeek-v2's from 69% to 51%. Qwen 3 Coder never asked under any prompt. The authors conclude that "prompt engineering alone proves insufficient" ([arXiv 2502.13069](https://arxiv.org/html/2502.13069)). For a Gemini-based agent this is a direct warning: a system-prompt line saying "ask when unsure" is close to a no-op.

Small models fail by guessing. When2Call, which scores the choice between calling a tool, asking and declining, finds that models often "produce a tool call with the missing parameters made up" where a question was right, and that scores **do not rise with size**: Qwen 2.5 7B and 72B both land at about 32–33 F1 ([arXiv 2504.18851](https://arxiv.org/html/2504.18851)). CAR-bench, an in-car assistant benchmark whose policy is close to Lunna's (resolve internally, ask only when two or more valid options remain, never guess between them), finds that **premature actions cause about 90% of GPT-5's disambiguation failures**. Thinking does not help, and no model passes 50% Pass^3 ([arXiv 2601.22027](https://arxiv.org/html/2601.22027v1)). The **68% Pass@3 against 36% Pass^3** gap for GPT-5 there is also independent support for the RFC's choice of pass^k as its metric.

What does work is structured uncertainty over tool arguments. SAGE-Agent assigns each candidate tool call a probability built from the schema: a parameter the user specified counts 1, an unspecified one 1/|domain|. It asks only when a question's expected value of perfect information, minus a cost for asking about the same aspect again, clears a threshold ([arXiv 2511.08798](https://arxiv.org/html/2511.08798)). On ClarifyBench's ambiguous queries with GPT-4o it reached **59.73% coverage at 1.39 questions**, against 42.88–55.70% at 2.07–3.42 questions for prompting baselines. The repeat-aspect penalty alone removed 18–27% of questions at under 3% cost. There is a trade-off the paper does not stress: on single-turn When2Call, SAGE-Agent's **ToolCall F1 fell below plain ReAct's** (0.65 against 0.75 on GPT-4o), even though its precision was highest. Gating questions on value buys better asking at the price of some correct calls. Two more studies point the same way. A Qwen3-1.7B clarifier trained with an information-gain reward reached 17.8 Pass@1 at 1.3 questions on τ-Bench, against 14.9 at 4.2 questions untrained, and success peaked at an intermediate budget because "excessive clarification introduces context pollution" ([arXiv 2606.03135](https://arxiv.org/html/2606.03135v1)). SpecBench's best agent first infers what it can, then asks one question per round with **four grounded options**, and reached 92% against 61–80% for the others ([arXiv 2606.20585](https://arxiv.org/html/2606.20585)).

Timing matters as much as volume. In *Ask Early*, a goal clarification injected 10% into the run recovered almost to the oracle (pass@3 0.78 against 0.80, with no clarification at 0.40). By 30% it was down to 0.50, and by 70% it was no better than never asking. Input clarifications decay more slowly but are worth little past about 50% ([arXiv 2605.07937](https://arxiv.org/html/2605.07937v1)). These runs were long (6–121 actions), so the curves do not transfer exactly to a 2–3-step calendar turn. The direction does: settle goal doubts ("which gym?", "move it or add another?") before a plan exists. Input doubts such as length can be defaulted and stated, because a Lunna proposal is reversible with one tap. That reversibility lowers the cost of acting compared with every benchmark above, which all assume irreversible actions. No paper tests it, and no paper compares default-and-state with asking for a missing duration. So the RFC's "30 min default, said in the reply" is a sound inference, not a measured result.

## Small models collapse on open multi-turn tool use, not on constrained classification

No public benchmark scores the candidates. BFCL's current snapshot (2026-04-12) has **no row for Gemini 3.1 Flash-Lite, any Gemini 3.x Flash, or Haiku 5.5** ([BFCL leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html)). Neither the 3.1 Flash-Lite model card nor the Haiku 5.5 announcement reports τ²-bench or BFCL ([DeepMind, Gemini 3.1 Flash-Lite card](https://deepmind.google/models/model-cards/gemini-3-1-flash-lite/); [Anthropic, Claude Haiku 5.5](https://www.anthropic.com/news/claude-haiku-5-5)). The closest evidence is the previous generation, and it is not encouraging for open-ended use. On BFCL, **Gemini 2.5 Flash-Lite scored 13.5% multi-turn and 1.5% on "missing function" turns** in native function-calling mode, against Haiku 4.5's 53.6% and 42.5%. Its memory score (state across turns) was 20.7% against Haiku 4.5's 54.4% ([BFCL data_overall.csv](https://gorilla.cs.berkeley.edu/data_overall.csv)). Its **irrelevance score of 92.5%** shows the shape of the failure: it rarely calls a tool when none applies, but it misses calls it should make (43.75% relevance). BFCL also shows that native function calling beats prompt-format tool use on every small model, by a wide margin (Haiku 4.5: 68.7% against 25.3%), so the agent should keep using OpenAI-compatible `tools`.

The evidence that tool design rescues small models is real but mostly indirect. LongFuncEval measured **7–85% drops as tool count grows, 7–91% as tool responses get longer, and 13–40% as conversations get longer** ([arXiv 2505.10570](https://arxiv.org/abs/2505.10570)). Each of those maps to an RFC lever: fewer verbs, a compact day, a fresh conversation per sheet. Anthropic's tool guide recommends "a few thoughtful tools", one scheduling tool instead of list-and-create, readable identifiers instead of UUIDs, and concise responses that used about a third of the tokens ([Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). Its SWE-bench poka-yoke change, requiring absolute paths, was then used "flawlessly" ([Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Vercel cut 80% of an agent's tools and went from 80% to 100% success with 42% fewer steps, though with a frontier model on five queries ([Vercel](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)). No controlled study compares one small model with consolidated against fragmented tools on a scheduling task. The RFC's bet, that a model which only classifies intent into a handful of gesture verbs with short refs avoids the multi-turn and missing-parameter weaknesses, is plausible and consistent with all of this, but untested.

On price and speed the comparison has flipped. Haiku 5.5, released 2026-10-07, lists at **$0.10 input / $0.50 output per 1M tokens** (under 100k prompt tokens), with $0.01 cache reads. Anthropic calls it its "fastest model to date" but gives no tokens-per-second figure ([Anthropic, Claude Haiku 5.5](https://www.anthropic.com/news/claude-haiku-5-5)). Its published agentic gains over Haiku 4.5 are large (OSWorld 15.7% to 72.4%), but those are computer-use and terminal suites, not tool-calling benchmarks like τ².

A turn whose output is a short tool call is dominated by TTFT multiplied by the number of round trips. No independent TTFT figure exists for any of the four, so p50 and p95 have to be measured from the NestJS server.

## Conclusion

The research moves the RFC's centre of gravity further toward its structural fixes. Caching and routing are configuration chores with little payoff at a 2k-token prefix and one call per turn. The real latency levers are fewer round trips, low reasoning effort and a client timeout. The model question is no longer "is flash-lite good enough for the price?". On list price, Haiku 5.5 now undercuts it by 2.5x, and a newer Flash-Lite exists. So the eval should run 3.1 Flash-Lite, 3.5 Flash-Lite, 3.8 Flash and Haiku 5.5 with the same harness and pick on pass^4. A provider switch to Anthropic would bring its own caching rules, which this research did not cover. The clarification literature adds one design consequence the RFC only implies: because Gemini models specifically under-ask, the eval needs ambiguous cases where the *server* must raise the doubt. It also needs a regression check that the model never overrides a server doubt by proposing anyway, since that guessing is the failure every study documents.
